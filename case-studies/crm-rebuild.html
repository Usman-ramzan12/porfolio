The Problem

A live production CRM with no documentation

The client had a legacy insurance sales portal running in production, handling real agents, real leads, and real revenue, but with no technical documentation, no tests, and no clean separation of concerns. They needed a complete rebuild on a modern stack without interrupting daily operations.

The challenge: before writing a single line of new code, I needed to understand every screen, every role, every business rule, and every edge case in the existing system, without touching its data.

My Approach

Read-only audit first, rebuild second

1

Read-only audit with Claude Code + Playwright MCP

Used Claude Code with the Playwright MCP server to crawl the live CRM in a strictly read-only mode, documenting every module, form field, state transition, and role restriction. Zero writes to production data.

2

Spec before code

Translated audit findings into a full schema, RBAC matrix, and feature spec. Defined the repository interface pattern upfront so the data layer (in-memory → Supabase) could be swapped without touching business logic.

3

Incremental, testable implementation

Built module by module on a feature branch, with every permission, form field, and state machine verified against the documented spec before merging.

Full-featured insurance CRM

The entire data layer sits behind a repository interface. The in-memory store used during development swaps to a Supabase/PostgreSQL backend without any changes to business logic, a clean migration path with zero risk to existing code.

Hard Problems Solved

What made this difficult

Recovering undocumented business logic from a live system safely

The biggest risk was misunderstanding an undocumented rule, a disposition transition that's only allowed for certain carriers on certain plans, or a permission that silently fails rather than showing an error. Using Claude Code with Playwright in read-only mode let me systematically click through every state in the live system and build a ground-truth spec before touching code.

Designing 198 permissions without making it unmaintainable

At 198 permissions across 13 sections, a flat permission table becomes a maintenance nightmare. The solution was a structured matrix: sections → resources → actions, with a role-inheritance model so adding a new section doesn't require manually granting 15 new permissions to every existing role.

Keeping the data layer portable without over-engineering

The repository pattern lets the app run entirely in-memory during development and CI, with a deterministic swap to Supabase for production, no environment-specific branches, no mocking infrastructure, no test database setup. The interface is thin enough that the Supabase implementation is a drop-in.
